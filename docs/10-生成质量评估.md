# 10 · 生成质量评估（人工打分）

> 判定器测的是**「像不像福尔摩斯」**，它测不出**「写得好不好」**。
> 这两件事必须分开量，否则答辩被问"你怎么评价生成质量"时会答不上来。

---

## 一、为什么要单独一套

现在的指标体系有一个明确的空洞：

| 已有 | 覆盖 | 缺口 |
|---|---|---|
| 判定器（8 轴 + 三档） | 角色一致性 | 不知道台词是否**吸引人**、是否**回应了场景**、是否**读起来像 1890 年代的人话** |
| 留出集（F01–F08） | 判定器的准度 | 判的是**人写死的候选文本**，不是模型生成的活稿 |
| 闭环 trace | 打回次数、耗时 | 不知道**每次打回有没有真的让稿子变好** |

一句话：**判定器能证明"没跑偏"，证明不了"写得好"。** 前者可以自动化，后者现阶段只能人评。

---

## 二、评什么（一维总分 + 三个二值检查）

刻意保持简单。评分者只有一个人（你），维度一多，信度就崩。

### 2.1 总分 `human_score`：1–5 整体可用性

问的问题只有一个：**"这段文字，你会不会直接放进自己的同人小说？"**

| 分 | 含义 | 锚点 |
|---|---|---|
| **5** | 直接用 | 语气、信息、时代感全对，且有一句让人想读下去的 |
| **4** | 小修即可 | 整体可用，可能有一处用词偏现代、或有一句略显平淡 |
| **3** | 方向对但不吸引人 | 信息正确，读起来像说明书；没有错，但也没有味道 |
| **2** | 需要大改 | 明显出戏、答非所问、或通篇泛泛而谈 |
| **1** | 不可用 | 完全跑偏：现代口吻、说教、OOC 到认不出人 |

### 2.2 三个二值检查（1 = 通过，0 = 不通过）

| 字段 | 判据 | 为什么单独列 |
|---|---|---|
| `period_voice` | 拼写是 en-GB、句法像 1890 年代的人说话（短句、克制、不用现代连接词） | **语体**问题，容易在"意思对"的情况下被忽略 |
| `on_scene` | 引用了场景里的**至少一处具体信息**（人名、物证、时间），不是泛泛而谈 | 模型最容易犯的错是"答得漂亮但不接题" |
| `no_anachronism` | 没有年代外概念、技术、称谓 | **事实**问题，与语体不同：`data` 是当年的词，`DNA` 不是 |

> `period_voice` 和 `no_anachronism` 的区别：前者问"这话像不像那个年代的人说的"，
> 后者问"有没有出现那个年代不存在的东西"。两者都会失败，但修法不同。

### 2.3 顺手记 `judge_score`

判定器对该稿打的分（0/1/2）从 trace 里抄过来。**它不是评分项**，是用来做同向性检验的：

> 如果 `judge_score` 越低的稿子，`human_score` 也越低，说明判定器的方向和人的审美是一致的。
> 这条比任何单点数字都重要——它回答"你的自动指标到底有没有意义"。

## 三、抽样方案（不许挑）

| 项 | 规则 |
|---|---|
| 场景数 | **10 个**，从 `data/golden/golden_holdout_f.json` 的输入里随机抽，或新写 10 条日常场景 |
| 每场景 | 跑完整闭环，**记录每一次 attempt 的草稿**（含被打回的） |
| 总样本 | 10 场景 × 1–3 稿 ≈ 15–25 条 |
| 来源 | 全部标 `source=loop_generated`，**不许手工润色后再评** |
| 盲评 | 打分时**不要看 judge_score**（先填 human_score 后填 judge_score） |

**三条禁则：**

1. 不许只挑"看起来会通过"的场景——那会把生成质量评成生成器的上限。
2. 不许评完再改场景——换题就是换分布。
3. 不许拿自己的评分去反推规则——那就变成第三轮自证。

---

## 四、指标口径（写死，不许事后改）

```
均分          = mean(human_score)
可用率        = count(human_score >= 4) / n          ← 创作者实际关心的数
硬伤率        = count(任一 check == 0) / n            ← 有一条硬伤就不能算可用
改写增益      = mean(human_score | attempt >= 2) − mean(human_score | attempt == 1)
同向性        = 按 judge_score 分组后的 mean(human_score)，看是否单调
```

**为什么改写增益是这个项目独有的指标：**
闭环每打回一次就多一段草稿。如果第 2 稿的均分不比第 1 稿高，那"打回重写"就是在烧钱。
这个数直接回答"你的闭环到底值不值"。

**n 很小的警告**（写进报告，别写进简历的标题）：
20 条里 1 条 = 5%。均分的置信区间很宽，只能说"趋势"，不能说"生成了 X 分"。

---

## 五、怎么和闭环打通

闭环的 `trace` 里已经有每稿的 `judge_score`、`hits`、`ms`。流程：

```
1. 跑 10 个场景：run_graph（或写个批量脚本循环 10 次）
2. 每次跑完，从输出里抄下每稿的：场景、attempt、judge_score、草稿
3. 填进 data/gen_eval/gen_scores.csv（judge_score 一列先留空）
4. 只读草稿打 human_score + 三个 check
5. 回头补 judge_score，排除顺序偏差
6. 跑 python -m src.cli.eval.score_generation 出报告
```

**第 4 步和第 5 步的顺序不能反**——先看 judge 分会污染你的判断，这是评测里最老的一条纪律。

## 六、效度威胁（必须写进报告，不然是自夸）

| 威胁 | 影响 | 应对 |
|---|---|---|
| **单评分者** | 无 inter-rater 信度，全是个人口味 | 找一个人帮你评 5 条，算粗略一致率；论文里叫"次级评分者" |
| **知道自己写的** | 会偏爱自己设计的场景 | 隔一天再评一遍，算 test-retest |
| **n≈20** | 一条样本 5%，差异不显著 | 只报均分与可用率，不报"提升了 X%"这种小数 |
| **单一生成模型** | 结论只对该模型成立 | 报告里写明模型名与版本（换模型等于换仪器） |
| **顺序偏差** | 先看的稿子印象更深 | 打乱顺序评；先评第 2 稿再评第 1 稿 |

---

## 七、跑法

```bash
# 填完 data/gen_eval/gen_scores.csv 之后
python -m src.cli.eval.score_generation
```

输出：样本数、均分、可用率、硬伤率、改写增益、按 judge_score 分组的同向性表。

## 八、这一条在答辩里怎么用

> "一致性我可以自动化，17 条未见样本上人机一致率 94.1%（qwen3.8-27b / F 集 / n=17；历史基线，
> 现主数 73.7% = qwen3.8-flash / G 集 / n=19，两数不同仪器不并排比），编造引文 0 条。
> 但『写得好不好』自动化不了，所以我又做了 20 条人工评分：均分 X、可用率 Y%、
> 硬伤率 Z%；而且被打回过的稿子均分比首稿高 W 分——这说明打回重写不是白花钱。
> 评分表、原始分数、汇总脚本都在仓库里，换个人可以重跑。"

**这段话的价值不在于分数高低，而在于它证明了：你知道自动指标覆盖不到哪里。**
