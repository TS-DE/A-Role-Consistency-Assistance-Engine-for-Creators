# 09 · 闭环与状态图（生成 → 判定 → 打回 → 人审）

> 对应代码：`src/graph/` + `src/cli/run_graph.py`。
> 判定器本身的分层见 [docs/08-判定器模块结构.md](08-判定器模块结构.md)。
>
> 这份文档回答四个问题：**状态怎么流、路由凭什么、坑在哪、怎么讲给别人听。**

---

## 一、一眼看懂

```
                        ┌──────────────────────────────┐
                        │                              │
START → generate → verify ──pass────→ finalize → END   │
          ↑            │                                │
          │            ├──rewrite→ rewrite ────────────┘
          │            │           （写 rewrite_notes 后回生成）
          │            │
          │            └──human──→ human(interrupt) → END
          │                          ↑
          └── 恢复：Command(resume=accept/edit/abandon)
```

五个节点，各管一件事：

| 节点 | 读 | 写 | 职责 |
|---|---|---|---|
| `generate` | `user_input` `rewrite_notes` | `draft` `attempt` | 唯一"创作"的地方 |
| `verify` | `draft` | `verdicts` `score` `violated` `verify_incomplete` | 8 轴取证 + 聚合 |
| `rewrite` | `violated` | `rewrite_notes` `score` | 把违规清单回灌给生成 |
| `finalize` | `draft` `score` | `final` `needs_human=False` | 通过出口 |
| `human` | `draft` `score` `violated` | `final` `needs_human=True` | 中断，等人裁决 |

---

## 二、状态契约（`GraphState`）

节点之间**不互相调用**，只读写 State。字段分四组：

```python
# 入口
user_input / character_id / history

# 生成
draft / attempt / rewrite_notes

# 校验
verdicts / score / violated / verify_incomplete

# 出口
final / needs_human / trace
```

三条约定：

1. **`total=False`**：每个节点只写自己负责的字段，不碰别人的。
2. **`score = -1` 表示"未完成"**，永远不等于通过。这个哨兵值很关键——缺一条规则算出的
   聚合分可能恰好是 `2`，那是假通过。
3. **`trace` 是 append-only 的日志**，每节点写一条（含 `ms`）。它是成本/延迟表的唯一来源。

## 三、一次请求的完整时序（实测数据）

```
generate a1  ms=4072    chars=1351
verify   a1  ms=58377   score=1  hits=1     ← 命中 1 条 soft
rewrite                    notes=1  next_attempt=2
generate a2  ms=3320    chars=1034
verify   a2  ms=30755   score=2  hits=0
finalize                  score=2
```

两稿、约 97 秒、一次打回后通过。这是答辩最该演的一段。

**耗时归因**（这条比数字本身值钱）：

| 环节 | 耗时 | 占比 |
|---|---|---|
| 生成 | 3–4 s | ~5% |
| **判定（8 次 fanout）** | **30–58 s** | **~95%** |

所以优化的着力点是判定，不是生成。判定已并发（`MAX_JUDGE_WORKERS=4`），
否则同样一轮要 155 s。

## 四、路由：三条决定，都不是技术问题

代码在 `src/graph/routing.py`，一个纯函数：

```python
if incomplete:              return HUMAN     # 1
if score == SCORE_PASS:     return PASS
if attempt >= max_attempts: return HUMAN     # 2
return REWRITE                               # 3
```

| # | 决定 | 理由 |
|---|---|---|
| 1 | `verify_incomplete` **立刻**转人工，不重试 | 判定没跑完时 `score=-1`，它既不是通过也不是违规。重试只会烧钱，网络瘫掉时会一路重试到天亮 —— 这是死循环，不是故障恢复 |
| 2 | 打回满 `max_attempts`（默认 3）转人工 | 再打回也大概率不变好，交给人比继续花钱划算 |
| 3 | **`score=1`（drift）也打回** | 宁可多花一次调用，也不放过"轻微漂移"。这是质量优先的取舍，代价是成本与延迟 |

**路由必须是纯函数**：冒烟脚本和 LangGraph 的条件边共用同一份判断。两处各写一遍，迟早漂移出
"演示时打回、上线时放行"的事故。

## 五、五个踩过的坑

### 1. 条件边不能写数据 → `final` 是空字符串

第一版 `pass` 直接连 `END`，结果 CLI 拿到的最终文本是 `""`。
因为条件边只决定"去哪"，不负责往 State 里写东西。补了 `finalize` 节点才修好。

> 这个坑手写 `while` 时不会踩（判断和赋值在同一段代码里），
> **是框架的约束逼你想清楚数据流**。

### 2. `interrupt()` 恢复时节点会从头重跑

所以挂起前**不能有副作用**（写文件、发请求），否则重放会做两次。
`human_node` 里只读不写，就是这个原因。

### 3. 串行判 8 条 = 白白浪费 8 倍时间

8 条 trait 彼此完全独立，串行只是历史遗留。并发后 155 s → 30–58 s。

### 4. 耗时归因错了两次

第一次以为"换便宜模型就快"（213→207 s，几乎没动）；第二次以为"生成慢"。
加了 `ms` 到 trace 才看清：**生成 3–4 秒，判定占 95%**。
**没有测量就没有判断** —— 这是这个项目里最实用的一条。

### 5. 人工放行必须留痕

`accept` 记成 `accepted_by_human`，**不要记成 pass**。
人工放行等于"系统本该拦住却让过了"，它是一条**漏杀**，要进统计。
没有这一步，"漏杀率"永远算不准。

## 六、和评测体系的关系（面试重点）

一套判定器，两种用法：

| 用法 | 入口 | 干什么 |
|---|---|---|
| **离线评测** | `src/cli/run_judge.py` | 拿固定的候选文本判分，和人标的 gold 比，算漏杀/误杀/一致率 |
| **在线闭环** | `src/cli/run_graph.py` | 判完就打回重写，判不准就转人工 |

同一个 `TraitEvaluator`，两条路径。所以：

- 闭环里发现的问题，能立刻用离线评测量化（比如"这条规则误杀率多少"）；
- 离线评测里改的规则，能立刻在闭环里看到行为变化（打回次数、最终通过率）。

**这就是"评测不是附庸"的意思**：没有离线指标，闭环就是一个凭感觉的重试机器。

## 八、与通用约束的对照

| 约束 | 落点 |
|---|---|
| SRP | 一个节点一个职责；路由是纯函数单独成文件 |
| OCP | 换后端（urllib→langchain）只加子类；换路由策略只改 `routing.py` |
| DIP | 节点依赖 `ChatModel` 抽象，不认识 urllib / langchain |
| 文件规模 | 最大 `builder.py` 约 140 行，其余 50–70 行，均 < 300 |
| 测试 | `tests/graph/test_<被测模块>.py`，19 个用例，含真实 interrupt/resume |
| 常量收敛 | `MAX_REWRITE_ATTEMPTS`、`INCOMPLETE_SCORE`、`MAX_JUDGE_WORKERS` 全在 `constants.py` |

## 九、答辩 3 分钟怎么讲

1. **30 秒：这是什么** —— "创作者写同人，AI 会把人设写崩。我做的是拦住它、并且能证明我拦得住。"
2. **60 秒：闭环怎么转** —— 生成 → 8 轴判定 → 不过就打回带证据重写 → 三次不过转人工。
   现场跑一次，展示第一稿被打回、第二稿通过。
3. **60 秒：凭什么说拦得住** —— 17 条未见样本、人机一致率数字、漏杀/误杀分开报、
   引文必须能在原文里逐字找到（编造 0 条）。
4. **30 秒：能搬去哪** —— 换一份 yaml 就是客服话术合规 / 品牌语气；同一套评测脚本不用改。

被追问时的三个必备答案：

- **"你怎么知道测试集不是自证的？"** → 留出集退役规则（docs/07 §七）、
  dev/回归/留出三层、变异测试待做。
- **"为什么用 LangGraph 不是 while？"** → 状态显式可 dump、可中断恢复（HITL 必需）、可画图。
- **"为什么不用微调？"** → 审不了别人的模型、给不出 judge 侧指标、规则改一行 vs 重训。
